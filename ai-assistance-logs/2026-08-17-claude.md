## 2. LLM response

This is a good plan, and the iTunes/iPod framing is more than a cute analogy — it names the one principle that makes e-paper software work: **all expensive, fiddly, high-interaction work happens on the desktop; the tablet only renders pre-baked artefacts.** I'd push that further than you have, and I'll flag the places where your current design still leaves computation on the device.

### On the architecture

**Precompute the calendar too, not just the papers.** Don't have the tablet derive "Today" from anything. Have the desktop tool emit a rolling window of day-files — say `days/2026-08-17.json` through `days/2026-09-16.json` — one per date, regenerated on every sync. The tablet's Today module then does nothing but load the file matching its own clock. No ICS parsing, no recurrence rules (which are genuinely horrible), no timezone maths on device, and it degrades gracefully: if you don't sync for a week, it's still correct. Same trick for Mems: have the desktop assemble a *dated deck*, one memory per day, months ahead, with its own spaced-resurfacing logic. The device just opens today's card.

**Make the modules data-driven.** Iterating on Android is slow and doubly so when your test device redraws at 2fps. So keep the app to a small set of render primitives — paginated text, card list, single full-screen card, checklist, clock — and have the desktop emit a manifest declaring which screens exist, what icon and label each gets, and which primitive renders it. Then "add a word-of-the-day module" becomes a desktop-side change with zero Kotlin. This is the single highest-leverage decision in the whole design.

**Your sync is one-way but your workflow isn't.** Notes, annotations, reading positions, checked-off habits, "I've seen this memo" all need to travel device→desktop. Add a device-writes-only `outbox/` that the desktop consumes and clears. Rule: never let both sides write the same path, and you never need conflict resolution.

**Consider prototyping as generated static HTML before committing to native.** Your desktop tool emits a small static site; a minimal WebView shell displays it. You'd validate the entire content pipeline and all your module ideas in a weekend instead of a month, and you'd learn which modules you actually open. The real costs are that you lose the vendor refresh-mode API and gesture control, so plan to port the keepers to native. If you do go native from the start, use plain Views rather than Compose — Compose's animations and ripples are everywhere by default and fighting them on e-paper is tedious.

**Check whether your vendor exposes a refresh-mode API.** If this is an Onyx device, `com.onyx.android.sdk` lets you request A2/fast/regal modes per-view and force full refreshes. That single lever will do more for perceived quality than any amount of UI design. It also gates whether building your own handwriting canvas is viable at all (see below).

### Your frictions, audited

| Friction | Status |
|---|---|
| PDF panning | Partly solved. Reflow fixes body text; figures, tables and display equations are the unsolved 80% of a research paper's value. |
| Personal org too heavy | Solved, and more cleanly than you proposed, via rolling day-files. |
| No mindful pipeline | The app is the easy half. The hard half is *ingestion*, and your plan doesn't address it. |
| Too much app/file switching | Solved. Add global search once content passes a few hundred items. |
| **Note-taking** | **Unaddressed.** It was your first stated use case and there's no Note module in your icon bar. |
| Device→desktop capture | Unaddressed (see outbox above). |
| Content decay | Unaddressed. Manual pipelines die. |

Three of those deserve expanding.

**On papers.** Build a source-priority ladder rather than one converter. If it's on arXiv, fetch the LaTeX source tarball — converting real LaTeX gives you clean structure, real equations, and figure files, and it's not close. If it's open-access biomedical, PubMed Central serves JATS XML, likewise structured. Only fall back to PDF extraction (Marker, Docling, MinerU) when neither exists. For equations, render LaTeX to SVG *on the desktop* so the tablet needs no maths renderer — precompute, again. For figures, extract them as separate assets, place them inline small, and make them tap-to-fullscreen: looking at a figure should be a deliberate act, not something you accidentally pan into. And for the genuinely un-reflowable PDF, keep a fallback path that crops margins and slices each A4 page into column-sized tiles — the old `k2pdfopt` approach turns panning into page-turning. Which is the general rule: **pagination everywhere, scrolling nowhere.** Every interaction should be one discrete refresh.

**On note-taking.** Low-latency ink needs the vendor's raw drawing path; a naive Canvas implementation will feel like writing with a delay pedal and you'll stop using it. I'd not build the ink engine. Either make Note a launcher that deep-links the stock notes app with a file in your synced folder, or restrict your Note module to typed/structured capture and leave handwriting to the vendor. Handwriting is the one place where "bespoke" costs more than it returns.

**On the mindful pipeline.** This lives or dies on how long it takes to add an item. If saving a quote takes five minutes of GTK form-filling, you will do it twice. Give yourself a one-keystroke path: a watched drop folder, a browser bookmarklet, a `mems add` CLI, a share target. Then let the desktop app be for *curating and scheduling* what's already been captured, not for capture itself. Also, put a cron or systemd timer on the whole build-and-sync step so the content refreshes without you thinking about it.

### Additional module ideas

Ranked by what I think actually earns a slot on a 7" e-paper screen:

- **Resurface** — a rotating item from your own old notes and highlights. If you have any kind of note archive, this is the highest-value contemplative module there is, and it's pure precompute.
- **People** — one person per day you might reach out to. Pairs beautifully with Mems and is the sort of thing that only works on a device you look at once, calmly.
- **Habits** — daily checkboxes. Big tap targets, one refresh per tap, writes to outbox. E-paper is genuinely better than a phone for this.
- **Edition** — a *finite* daily bundle of pre-fetched articles, RSS, newsletters, reflowed. Capped at N items. The finiteness is the feature, and it's a much stronger answer to "mindful consumption" than a folder of saved links.
- **Sky** — sunrise, sunset, moon phase. Computable offline from a lat/long, needs no sync, quietly lovely.
- **Now** — a single sentence about what you're working on this season. A contemplative anchor; costs almost nothing to build.
- **Lists** — packing, shopping, recurring checklists.
- **Ref** — static cheatsheets you'd rather not reach for a laptop to see.
- **Words** — spaced-repetition cards, deck built on the desktop, scheduling precomputed.
- **Year** — year-progress or life-in-weeks. Divisive; some find it motivating, some find it grim.

I'd resist building more than five or six for v1. With a data-driven manifest, the rest cost you a config entry each, so let usage decide.

### Naming the modules

The governing principle: an icon bar has the icon doing the recognition work and the label doing the reminding, so favour real words over truncations, and keep the register consistent. Mixing `Today` with `Cdown` is the jarring part more than `Cdown` itself.

A clean 3–4 character set: **Day · Week · Read · Note · Soon · Keep · Sync**

Notes on the substitutions. `Sync` for Reload is strictly better — same length, and it's the honest word for what the button does. `Soon` for Cdown reads well and generalises past deadlines to birthdays and trips; `Until`, `Ahead` and `Dates` also work. For Mems: **Keep**, **Dwell**, **Echo**, **Attic**, **Pause**, **Trove** — I'd take `Dwell` if you want the module to have a mood and `Keep` if you want it to have a function. `Day` over `Today` gains you symmetry with `Week` and a character. If you'd rather have flavour than uniformity: **Today · Week · Shelf · Ink · Until · Dwell · Sync**.

### Naming the suite

The printing trades give you a metaphor family that maps exactly onto your architecture — the desktop sets type and imposes sheets, the device displays finished pages:

- **Quire** (device) / **Press** (desktop) — a quire is a gathering of folded sheets. My favourite: short, real, unclaimed, and the pairing explains itself.
- **Folio** / **Compositor** — a compositor is the person who sets the type. Slightly grander.
- **Slate** / **Quarry** — leans on the e-paper feel rather than the pipeline.
- **Leaf** / **Press** — leaf as in page.
- **Codex** / **Scribe**.

Or take one name and suffix it: `quire` and `quire-press`, which keeps your repo and your mental model simple.

### A few smaller things

Set body text in something with sturdy stems and a generous x-height — Literata, Charis, Bitter, Atkinson Hyperlegible — and avoid light weights and hairline serifs entirely. Pure black on pure white, no grey text; on Kaleido the colour filter array costs you a little contrast and you don't have any to spare. Use colour sparingly and semantically — a red rule for a deadline today, a fill on a badge — never for small text, since colour resolution is roughly a third of mono.

Store content as many small files rather than one database: rsync stays incremental, you can diff and version it, and you can inspect it by hand when something looks wrong. A manifest with content hashes lets the app show you what arrived since last sync, which is a nice thing for the Sync screen to display.

Finally, one ergonomic point: on a 7" device held in the right hand, a left-side icon bar is a reach. Worth making the side configurable, or at least deciding deliberately rather than by CSS default.

**The rail bug** was the flexible spacer that pushes Settings to the bottom of the bar. It was `MATCH_PARENT` wide, and a bare `View` returns the full spec size from `getDefaultSize()` for `AT_MOST` as well as `EXACTLY` — so inside a `wrap_content` rail it measured to the entire screen width, dragged the rail's width with it, and left the content pane the zero pixels remaining. That's why fonts loaded fine: nothing was wrong with the payload, only the measurement.

The spacer is now an explicit `LayoutParams(0, 0, 1f)`, since only a non-negative dimension yields `EXACTLY(0)` — `WRAP_CONTENT` would have had exactly the same bug. I also gave the rail a fixed `@dimen/rail_width` of 64dp rather than `wrap_content`, both as belt-and-braces and because a rail that resizes when a label changes makes the reading column jump.

While in there I found two more places relying on the same accident — the module header and the Day/Week navigation rows were only full width because a `MATCH_PARENT` rule inside them stretched their `wrap_content` parent. They rendered correctly, but by luck. Both are now explicit, with a comment naming the trap so it doesn't come back.

**The icon** is an adaptive icon: green leaf foreground on a plain white background, wired up as `android:icon` and `android:roundIcon`. minSdk is 29 so adaptive-only is sufficient and no PNG densities are needed.

I rendered it rather than trusting the coordinates, which was worth doing — my first two attempts looked like a feather, not a leaf. The veins overshot the blade edge and read as notches, the stalk fell outside the 72dp safe zone where a circular mask would clip it, and the shape was too narrow because the arc construction I'd used couldn't be widened. The final version is built on the leaf's own axis with explicit perpendicular control offsets, giving a proper 0.6 width-to-length ratio, veins length-tapered to the local blade width so none breaks the edge, and everything inside 32 of the 36-unit safe radius. Checked legible down to 48px. Midrib and veins are knocked out in white rather than drawn in a second green, because one saturated mass against white is what survives Kaleido's colour filter — a tint would come back grey.
